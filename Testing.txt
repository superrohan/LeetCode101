# Implement Database-Driven Location-Based Filtering for Remediation Overdue Notifications

You are working on an existing Java Spring Boot application called **Notification Router**.

The application receives emails from BigID through SMTP, identifies notification types, evaluates database-backed rules, and decides whether to FORWARD, SUPPRESS, or PASS_THROUGH notifications.

The existing application already supports:
- Inbound SMTP email reception.
- Remediation Overdue notification classification.
- Database-backed notification rules.
- FORWARD, SUPPRESS, and PASS_THROUGH actions.
- Notification processing and delivery tracking.
- SQL Server database with Flyway migrations.

## 1. Business requirement

The BA has clarified the requirement.

We do NOT want a generic rule that forwards all Remediation Overdue notifications.

We need to filter **Remediation Overdue notifications based on datasource location and datasource type (CID or CREDENTIAL)**.

The Operations team must be able to enable or disable notifications independently for every location and datasource type by changing database rules.

There must be NO hardcoded list of locations or hardcoded location-specific filtering rules in Java code.

## 2. How BigID generates the subject

BigID's existing notification subject template is:

`cDev: [Action Required] Remediation overdue notification - ${datasourceName}`

BigID dynamically replaces `${datasourceName}` with the actual datasource name.

Examples:

**CID datasources:**
- `CH-SHRPNT`
- `UK-GITLAB_FileLocation_Embedded_files_PPT_SCANNING_QA6_001`
- `HK-<datasource-name>`

**Credential datasources:**
- `AM-ONEDRV-CRED-Cloud-43490091_US_001`
- `AM-ONEDRV-CRED-Cloud-43490091_US_002`
- `AM-ONEDRV-CRED-Cloud-PI18_QA_001`

Important naming conventions:

1. The location prefix is ALWAYS the first two-letter code before the first hyphen.
2. This applies to BOTH CID and CREDENTIAL datasources.
3. Examples:
   - `CH-SHRPNT` → location `CH`
   - `UK-GITLAB_...` → location `UK`
   - `AM-ONEDRV-CRED-...` → location `AM`
4. Do NOT extract the location from `_US_001` or any other part of the datasource name.
5. A datasource is classified as CREDENTIAL when its name contains the standalone `CRED` token, separated by hyphens. Otherwise, classify it as CID.
6. Do not assume that every datasource name containing the letters `CRED` anywhere is necessarily a Credential datasource. Use token-based matching.

## 3. Required database-driven rule structure

Inspect the existing `notification_rule` table, entity, repository, and rule engine.

Extend the existing rule model rather than creating an entirely new rule management system.

The rule must support these attributes:

- `id`
- `name`
- `enabled`
- `priority` (preserve if currently used)
- `notification_type`
- `datasource_type` (CID or CREDENTIAL)
- `location_prefix` (for example CH, UK, HK, AM)
- `action`
- `created_at`
- `updated_at`

Reuse existing columns and conventions wherever possible.

If `datasource_type` and `location_prefix` do not exist, add them through a new Flyway migration. Do NOT modify an already-applied migration.

Add an appropriate unique constraint or unique index to prevent duplicate rules for the same notification type, datasource type, and location prefix.

Ensure compatibility with the existing SQL Server database and Flyway conventions.

Do not introduce hardcoded location lists into application code or database seed migrations.

## 4. Required notification processing flow

For every inbound email:

### Step 1: Classify notification type

Continue using the existing notification classifier.

Do not break or replace the current Remediation Overdue classification logic unnecessarily.

### Step 2: Non-Remediation Overdue notifications

If the email is NOT classified as `REMEDIATION_OVERDUE`:

- Preserve the existing notification processing behaviour.
- Preserve existing PASS_THROUGH behaviour where applicable.
- Do not apply the new location-based filtering logic.

### Step 3: Extract datasource name

For Remediation Overdue notifications:

- Extract the datasource name from the subject.
- Use the existing subject format as the basis for extraction.
- Account for the configured subject prefix and suffix.
- Handle case and whitespace consistently.
- Do not assume the datasource name is always a single fixed value.

If the subject does not contain a valid datasource name, SUPPRESS the notification.

### Step 4: Determine datasource location

Extract the first two-letter prefix before the first hyphen.

Examples:

| Datasource name | Location |
|---|---|
| CH-SHRPNT | CH |
| UK-GITLAB_FileLocation_Excel... | UK |
| HK-<datasource-name> | HK |
| AM-ONEDRV-CRED-Cloud-43490091_US_001 | AM |

Validate the extracted prefix. If the datasource name is malformed or the prefix cannot be extracted, SUPPRESS the notification.

Do not maintain a hardcoded list of accepted locations. The database rules determine which locations are configured.

### Step 5: Determine datasource type

Classify the datasource as:

- `CREDENTIAL` if the datasource name contains the standalone hyphen-delimited token `CRED`.
- `CID` otherwise.

Examples:

- `AM-ONEDRV-CRED-Cloud-43490091_US_001` → CREDENTIAL
- `AM-ONEDRV-Cloud-43287229` → CID
- `CH-SHRPNT` → CID

### Step 6: Exact database rule lookup

Look up a rule using all three attributes:

- `notification_type = REMEDIATION_OVERDUE`
- `datasource_type = extracted datasource type`
- `location_prefix = extracted location`

The lookup must be deterministic and must not accidentally select a generic Remediation Overdue rule.

### Step 7: Apply the rule

Expected behaviour:

| Matching rule | Enabled | Decision |
|---|---|---|
| Exists | true | FORWARD |
| Exists | false | SUPPRESS |
| Does not exist | N/A | SUPPRESS |
| Datasource type unknown | N/A | SUPPRESS |
| Location missing/invalid | N/A | SUPPRESS |
| Subject malformed | N/A | SUPPRESS |

**Critical business rule:**

For Remediation Overdue notifications, missing or unmatched location rules MUST result in SUPPRESS.

There must be NO fallback to the existing generic `REMEDIATION_OVERDUE + FORWARD` rule.

This is important because an unknown location or an unconfigured datasource must never accidentally generate an email.
